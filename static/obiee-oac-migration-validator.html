Compatibility Checks

What the Validator Catches

OAC's query engine handles several Logical SQL patterns differently from OBIEE 11g/12c. These four changes cause the most report failures post-migration.

🔴

Comma-Join Syntax → Explicit JOIN Required HIGH

OBIEE tolerated implicit comma joins in Logical SQL (FROM "Subject A", "Subject B"). OAC enforces explicit join syntax. Reports using comma joins produce assertion failures (nQSError: Assertion failure) in OAC. The validator detects comma joins and outputs the corrected OBIEE JOIN syntax.

🔴

saw_X Subquery Aliasing HIGH

OBIEE's internal SQL uses saw_0, saw_1 aliases in nested queries. Reports that reference these aliases in custom SQL overrides or OBIEE Answers advanced SQL break in OAC where the aliasing scheme changed. Validator flags these and suggests the OAC-compatible column reference format.

🟡

Missing GROUP BY on Ranked Aggregates MED

OBIEE's query rewriter was more permissive about implicit grouping in aggregate queries. OAC enforces strict GROUP BY requirements. Reports using RANK(), DENSE_RANK(), or SUM() without explicit GROUP BY clauses that worked in OBIEE will throw syntax errors in OAC.

🟡

Deprecated Column Alias Formats MED

Several OBIEE-specific column alias patterns (particularly in Presentation layer references) changed format between OBIEE 12c and OAC. Reports with hardcoded subject area paths in non-standard format produce "column not found" errors. Validator normalizes these to the OAC expected format.
