PER_PERSONS and PER_ALL_PEOPLE_F: Where Person Identity Starts

November 23, 2026 19 min read
Oracle HCM Tables

PER_PERSONS and PER_ALL_PEOPLE_F answer different questions in Oracle Fusion HCM: one represents person-level identity, while the other stores effective-dated person records. Join them on PERSON_ID, then apply the right as-of date before adding names, assignments, or other relationships.

Key Takeaways

  • Where does person identity start? Use PER_PERSONS for the person-level identity record and PER_ALL_PEOPLE_F for effective-dated person data.
  • Which table supplies the person number? Select PERSON_NUMBER from PER_ALL_PEOPLE_F, not PER_PERSONS.
  • What is the join? Match the tables on PERSON_ID; add effective-date predicates to select the record valid on your report date.
  • How do you avoid inflated row counts? Define the report grain, then add names, assignments, and other one-to-many relationships one at a time.
  • Need to inspect Oracle Fusion schema fields? Use Oracle Cloud Tables to search HCM tables and columns alongside other Fusion Cloud schema areas.
  • How should sensitive data be handled? Select only fields required for the report and limit access and downstream sharing to the report’s purpose.

Separate the person identity from the effective-dated person record

PER_PERSONS is the person-level identity record. PER_ALL_PEOPLE_F is the effective-dated person record, so it can contain different versions of a person’s data across effective date ranges.

Use PERSON_ID to connect the two. When a report needs a person number, select PER_ALL_PEOPLE_F.PERSON_NUMBER; PERSON_NUMBER is not a column to look for in PER_PERSONS.

Oracle documents PERSON_NUMBER in PER_ALL_PEOPLE_F as VARCHAR2 with a length of 30. Select only the identity fields the report needs instead of pulling every available column.

Keep START_DATE separate from EFFECTIVE_START_DATE and EFFECTIVE_END_DATE. START_DATE is a person-related business date; the effective-date columns define the period during which a particular row version applies.

Join the tables on PERSON_ID

Join PER_PERSONS to PER_ALL_PEOPLE_F with p.PERSON_ID = papf.PERSON_ID. Oracle defines PERSON_ID as NUMBER with precision 18 in PER_PERSONS and as NUMBER with precision 18 in PER_ALL_PEOPLE_F.

For a report as of a particular date, select the row whose effective range includes the bound date. Start with this two-table query before joining additional HCM relationships:

SELECT
    p.person_id,
    papf.person_number,
    p.start_date,
    papf.effective_start_date,
    papf.effective_end_date
FROM per_persons p
JOIN per_all_people_f papf
  ON papf.person_id = p.person_id
 AND papf.effective_start_date <= :as_of_date
 AND papf.effective_end_date >= :as_of_date;

Bind :as_of_date as a date value. The inclusive range predicates select the PER_ALL_PEOPLE_F version valid on that date; joining only on PERSON_ID can return multiple historical versions.

Use a left outer join when the report must retain every PER_PERSONS row, including people without a matching PER_ALL_PEOPLE_F row for the selected date. Put the date conditions in the ON clause, not the WHERE clause:

SELECT
    p.person_id,
    papf.person_number
FROM per_persons p
LEFT JOIN per_all_people_f papf
  ON papf.person_id = p.person_id
 AND papf.effective_start_date <= :as_of_date
 AND papf.effective_end_date >= :as_of_date;

A WHERE condition on papf can discard rows where the outer join found no match. The Join Path Finder suits this stage because it helps find join columns between two table names; verify that the suggested path matches the relationship and row grain your report requires.

Apply one as-of date consistently

A historical report is only coherent when its effective-dated tables use the same point in time. Apply the same :as_of_date to PER_ALL_PEOPLE_F, PER_PERSON_NAMES_F, and PER_ALL_ASSIGNMENTS_M instead of combining a past person record with a current name or assignment.

Use the inclusive predicate EFFECTIVE_START_DATE <= :as_of_date AND EFFECTIVE_END_DATE >= :as_of_date for each date-effective row. Keep each table’s predicates in its own join condition when unmatched rows must remain in the result.

For example, a name join can use the same report date as the person record:

LEFT JOIN per_person_names_f ppnf
  ON ppnf.person_id = p.person_id
 AND ppnf.effective_start_date <= :as_of_date
 AND ppnf.effective_end_date >= :as_of_date

Do not use START_DATE as a substitute for effective-date boundaries. It describes a business date, while EFFECTIVE_START_DATE and EFFECTIVE_END_DATE determine which version of a date-effective row applies.

Add names, assignments, service periods, and person types deliberately

Retrieve names from PER_PERSON_NAMES_F, align its effective range with the report date, and choose the name type that fits the output. A person-to-name join is not automatically one-to-one, so decide which name record the report should show.

Use PER_ALL_ASSIGNMENTS_M for assignment details. A person can have multiple qualifying assignments, so define which assignment types and statuses belong in the report before deciding how to reduce the result to one row per person.

Use PER_PERIODS_OF_SERVICE for work-relationship periods. A rehire can result in multiple periods of service for one person, which means a person-to-service-period join naturally returns more than one row.

For person type, use PER_PERSON_TYPE_USAGES_M and PER_PERSON_TYPES. Account for effective dates and multiple type usages; inferring a person’s type from the person row skips the table that represents the usage relationship.

When building a name-and-assignment extract, add each join with its own date and business criteria. For a specific name type, bind or filter the intended type; for assignments, state the assignment population the report is designed to include.

Diagnose duplicate rows by checking each join

Your query returns repeated PERSON_ID values. That does not automatically mean the join is wrong. First record the intended grain: one row per person, assignment, or period of service.

  1. Run the person-table join by itself and record total rows and distinct PERSON_ID values.
  2. Add the name relationship, then compare both counts.
  3. Add assignments and other relationships one at a time, repeating the count comparison after each join.
  4. Check each effective-date predicate and the intended name, assignment, and person-type criteria before diagnosing a faulty join.

If the row count increases while the distinct person count stays constant, the added relationship is returning multiple rows per person. That may be correct at the relationship’s grain; it is a problem only if the report promises one row per person.

When several one-to-many relationships are involved, select or aggregate the intended row set for each relationship before combining them. Otherwise, multiple names, assignments, and service periods can multiply each other into combinations that do not match the report’s intended grain.

Handle personal data and flexfields with care

Birth details, national identifiers, and other sensitive personal fields belong in a report only when there is a clear business need and the report user has authorization. Use an explicit column list instead of SELECT * so unneeded fields do not flow into report output.

Apply the same discipline to extracts, exports, and downstream sharing. Limit both the selected data and its audience to the report’s stated purpose.

Treat ATTRIBUTE and related descriptive flexfield columns as configurable fields. Their business meaning can vary by implementation, so a column name alone does not establish a universal definition; document the configured meaning used by your report.

Frequently Asked Questions

Can PERSON_NUMBER change when a person is rehired?

A rehire can create another work relationship for the same person, so a new service period does not by itself establish a new person identity. Whether your implementation changes a person number is a numbering and configuration question, not something to infer from the presence of a new assignment.

What does BUSINESS_GROUP_ID represent, and when should it be used as a filter?

BUSINESS_GROUP_ID identifies the business group associated with a row. Use it when the report’s intended population is explicitly limited to that business group, rather than treating it as a general substitute for assignment, legal employer, or effective-date criteria.

How can I return people who have no assignment?

Use a correlated NOT EXISTS against PER_ALL_ASSIGNMENTS_M, matching on PERSON_ID and applying the report date and assignment criteria inside the subquery. This tests for the absence of a qualifying assignment without multiplying the person rows.

SELECT p.person_id
FROM per_persons p
WHERE NOT EXISTS (
    SELECT 1
    FROM per_all_assignments_m a
    WHERE a.person_id = p.person_id
      AND a.effective_start_date <= :as_of_date
      AND a.effective_end_date >= :as_of_date
);

Is PERSON_ID a suitable identifier to expose in reports for end users?

PERSON_ID is a system key suited to joining records, not usually a meaningful display value for a business audience. Choose a user-facing identifier appropriate to the report’s purpose and audience, and reserve internal keys for technical use where practical.

Which table should supply birth and other person-level details?

Use PER_PERSONS for person-level attributes defined there, such as date of birth. National identifiers have their own data relationship, so retrieve them through the table that owns that identifier.

Conclusion

PER_PERSONS and PER_ALL_PEOPLE_F mark the start of the Oracle Fusion HCM person model, but they serve different roles: person identity and effective-dated person data. Join on PERSON_ID, select PERSON_NUMBER from the correct table, and apply one as-of date consistently.

Then add names, assignments, service periods, and person types according to the report’s required grain. Test each relationship separately, and keep sensitive fields and configurable flexfields within the report’s actual purpose.
