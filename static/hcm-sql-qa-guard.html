The 5 Checks

What QA Guard Catches

Every check targets Oracle HCM-specific SQL patterns that pass syntax validation but produce silent data quality failures in production.

🔴

Missing EFFECTIVE_LATEST_CHANGE = 'Y' HIGH

Queries against PER_ALL_ASSIGNMENTS_M, PER_ALL_PEOPLE_M, or any _M table without an effective date constraint return all historical rows. A 5,000-employee org returns 15,000–30,000 rows instead of 5,000. This is the #1 cause of wrong headcount in OTBI reports.

🔴

Deprecated _F Table References (24B+) HIGH

Queries using PER_ALL_ASSIGNMENTS_F directly when PER_ALL_ASSIGNMENTS_M is the Oracle-recommended view. Oracle's new OTBI subject areas don't join to _F tables, causing mismatches when reports are later migrated. Flag and suggest the _M equivalent.

🔴

SELECT * on Fact Tables HIGH

Selecting all columns from PER_ALL_ASSIGNMENTS_M (350+ columns) or PAY_RUN_RESULTS causes full-table scans and can exhaust Oracle's row fetch limits in OTBI. One developer doing this in a report that later gets scheduled weekly creates a performance incident.

🟡

Unbound Date Ranges MED

Payroll queries against PAY_RUN_RESULTS or PAY_PAYROLL_ACTIONS without a date range bound scan every payroll run ever processed. On a 10-year-old Oracle instance, this is millions of rows. A missing AND pa.effective_date >= ADD_MONTHS(SYSDATE, -12) costs minutes of runtime.

🟡

DISTINCT Masking Join Duplication MED

SELECT DISTINCT on a query against _M tables indicates an unresolved Cartesian join. The DISTINCT hides the symptom but not the root cause — when the query is later embedded in a union or CTE, the duplication re-emerges. QA Guard flags this and suggests the correct effective date filter instead.

Example — Query Submitted to QA Guard
-- Consultant's query before QA Guard review
SELECT DISTINCT
  p.person_number,
  p.full_name,
  a.*                -- ❌ SELECT * on _M table
FROM   per_all_assignments_f a    -- ❌ Deprecated _F table
JOIN   per_all_people_f p
  ON   p.person_id = a.person_id
WHERE  a.assignment_type = 'E';  -- ❌ No effective date filter

FAQ

Common Questions

Does QA Guard execute my SQL against my Oracle instance?

No. QA Guard performs static analysis on your SQL text — the same way a linter works on code. No database connection required. Your query never leaves the tool, and no data is accessed.

What Oracle HCM versions does it cover?

QA Guard covers Oracle Fusion Cloud HCM (all release versions from 23A onward). The anti-patterns it catches apply across all current cloud releases. Oracle EBS is not supported — it's a different schema architecture.

Can I configure which checks to run?

Yes — on the Partner Firm tier, you can enable/disable individual checks and set severity thresholds per your firm's delivery standards. Useful if your team uses a different effective date convention internally.

What does the PDF report include?

The PDF includes: QA score (0–100), per-check results with severity ratings, the specific SQL line triggering each flag, and remediation snippets showing the corrected pattern. Partners typically attach this to deliverable documentation for clients.
